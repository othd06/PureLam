
# The Philosophy Of PureLam

First and foremost PureLam is intended to be an **implementation** of the lambda calculus **in a manner that is faithful to the semantics and ergonomics of the lambda calculus's use in pen-and-paper**.

This means that all general computation ought to be performed entirely within the semantics of the calculus itself. As a result there is not and **will never be** features such as the following:
 * Language-Level recursion
 * Direct computation on native machine values
 * Language-Level pattern matching
 * Static Types
 * Generic side-effects
 * etc...

PureLam does not, however, insist on strictly zero extensions over the formal lambda calculus as published by Alonzo Church in 1936. For instance, PureLam includes a preprocessor system for modules and definitions which is not included in the formalisation of the untyped lambda calculus however it does replicate functionality that is near universally used by actual pen-and-paper applications of the calculus which is shorthands.

Similarly, since the intention is to write usable code, PureLam does need some sort of IO story. There are two levels to this. The first of these is entirely within the semantics of the calculus (already allowing for the existence of a preprocessor system) which is the use of `io-input` for textual inclusion of user inputs and the automatic printing of terms post-evaluation. The second of these does borrow from the Lambda-Delta calculus published by Church in 1941. This calculus added semantic values, a set of delta-rules that operate on these values, and delta-runes which can be used to invoke them. Obviously, this is a fairly major semantic extension to the untyped lambda calculus in that it allows for general computation on native semantic values which is something that PureLam is explicitly committed to not allowing. PureLam, however, borrows an incredibly restricted version of this system that performs only enough to translate to and from native semantic values but no further. The intention of this is to ensure that the IO story of PureLam is not forced to require users to read and interpret canonical encodings at every stage of the program. While it does certainly pollute the semantics compared to pen-and-paper applications which can simply retain the shorthand encoded value wherever it is known that it is intended to be interpreted as an encoding, this is deemed as the best compromise between remaining faithful to the original semantics of the lambda calculus whilst also remaining faithful to the ergonomics of the pen-and-paper calculus as it is actually used.

As you can see, the goal of PureLam is firmly **not to create a semantically distinct functional programming language** but rather to provide a small, faithful runtime together with enough syntax and tooling to make programming in the pure untyped lambda calculus practical.

This is also the motivation behind providing an extensive set of standard libraries. Each library is modular meaning you can import some, all, or none of the libraries you want depending on how much functionality you want versus building it yourself. Crucially, also, the libraries are written entirely in PureLam itself meaning that it is guaranteed that they cannot deviate from the semantics enforced by the runtime whilst adding the ability to utilise a wide range of features from a comprehensive mathematics library, to named combinators, to Haskell-style Monads. Since these do not add to the semantic core, and can indeed be ignored entirely if they are unwanted, they are the perfect embodiment of semantic faithfulness with usability.

Another key philosophical commitment is not to conceal characteristics that are idiosyncratic of the untyped lambda calculus. The key example of this is the way in which the lack of native semantic values forces the use of encodings. It is for this reason that, where there exists a diversity of encodings for a given semantic object, the standard library **does not assume which encoding is used**. The technical solution to this is what the standard library typically calls typeclasses where a "type" refers to some convention over an encoding rather than a language/runtime enforced static or dynamic type. In this way, standard library typeclasses are effectively a meta-convention introduced by the standard libraries to encode conventions themselves. The result is that, for instance, both Church-lists and Scott-lists are implemented already but if you wanted to, instead, use pair-lists it would be perfectly possible simply by defining a pair-list typeclass defining the core primitive operations belonging to list encodings (chosen to allow every encoding to benefit from the performance characteristics it uniquely has, rather than as a minimal set of operations) and then use the list operators in `std/compounds` by simply writing `Nil Pair-List`, `Cons Pair-List`, `Map Pair-List` etc... and changing nothing else about the code. Were this not to be included in the standard libraries then they would have violated the underlying philosophy of PureLam in that it would have concealed a unique feature of the untyped lambda calculus, multiple encodings, in favour of offering preference to a single encoding over any others.

Unfortunately, this does not extend to the delta-rules mentioned earlier however if you encounter an encoding you wish to use and expect that others may as well, please feel free to submit either issues or pull requests describing the encoding so that it can be added to the IO system.

So now that we know that PureLam is meant to be faithful both to the semantics of the abstract untyped lambda calculus and to the ergonomics of the pen-and-paper untyped lambda calculus, the final piece of the puzzle is that PureLam intends to, within those very minimalist bounds, be as maximalist as possible. As a result the default evaluation strategy will guarantee finding a normal form where one exists without causing a callstack overflow but will improve performance as much as possible (including diverging from full normal order evaluation where it is safe to do so). Similarly, it is absolutely intended to add features like command-line flags for different evaluation strategies, printing performance metrics, and any other feature that exists around and outside the calculus to make it as expressive and exploratory as possible without violating the fundamental semantics. Indeed, the standard library mentioned earlier can be seen as an extension of this final philosophical point.

A final note on versioning. It is mentioned in the [README](README.md) that it is currently intended that there will be no 2.0.0 as it is expected that no breaking changes will be needed. This too, is a serious philosophical commitment about stability. The 3 main anticipated potential use cases for a tool like this are hobbyists, education, and research. For at least two of those use cases it is important that there be serious stability guarantees that code written on 1.0.0 will work on all 1.x.x versions (and, equally for any other earlier and later minor/patch version). This does not mean that some things will not be unstable, for example the 1.0.0 release will not use capture-free shorthands for the `define` keyword despite this being expected for 1.1.0 but it does mean that any such instabilities, in the core runtime or in the standard libraries, will be clearly documented with obvious ways to ensure that older behaviour is preserved (in this case, by using `define-unsafe`). Furthermore, since PureLam is intended to be research-grade, this will include not only functionality but also relative performance of equivalent code (Note: this does not extend to include that any changes to the standard libraries must be equally performant as this is not "equivalent code" so if you want standard library code but care about relative performance then it is recommended that you  obtain the source for the specific version and import it yourself manually). This means that, for instance, the second the default evaluator is upgraded beyond pure normal order evaluation, a command line flag will be provided to, at the very least, switch back to pure normal order evaluation and this is documented clearly in the README from 1.0.0.

And that, dear comrades, is the guiding philosophy of PureLam.
